Five-stage datapath

  1. IFFetch an instruction.
  2. IDDecode and resolve operand hazards.
  3. EXExecute and form addresses.
  4. MEMComplete data access.
  5. WBWrite back results.

My responsibilities

  • Completed the initial individual CPU and pipeline labs, including forwarding and stall handling.
  • Implemented address, alignment, breakpoint, and illegal-instruction exception paths.
  • Worked with a teammate on SRAM-like handshakes and AXI control; the standalone AXI bridge was another teammate’s responsibility.
  • Implemented TLB exception handling and integrated D-cache and uncached access paths. The base TLB and cache modules were developed by teammates.

A debugging case: stale instructions after an exception

An FPGA test intermittently stalled even though the initial simulation passed. Varying memory latency helped reproduce the problem and trace it to fetch-buffer state that survived an exception flush.

Another issue involved stores taking effect in EX before an older exception reached WB. The design needed to suppress those side effects early; flushing at writeback could not undo a completed memory write.

Measured result and validation boundary

¹ Forwarding experiment: recorded functional-test simulation time decreased from 1,330,995 ns for the stall-based version to 604,455 ns for the forwarding version, a 54.6% reduction. Both runs recorded PASS. This is one simulation workload, not a clock-frequency improvement or a general application speedup.

Reports document simulation and FPGA passes for several stages, including exp22. The later exp23 cache-maintenance work still had an unfinished CACOP mode=2 path; the whole final design is not claimed to have passed every test.
